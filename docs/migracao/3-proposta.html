Proposta

O que já foi decidido sobre a migração, o que está em debate e o que ainda não foi discutido. Cresce conforme a conversa; nada entra como decidido sem passar por você.

Decidido

Premissa

CamadaLinguagemO que éRegra
CORERustToda a lógica do app: modelos, estado, regras, persistência, git, rede, protocolo e rotas do socket.Só usa o que é igual em qualquer plataforma. Testável com cargo test, sem app aberto.
DRIVERRustAcesso ao sistema que difere por plataforma: pty, processos e sinais, conexão local com pid do par, TCC, notificação, troca do app na atualização.Implementa traits que o core define. É a única parte reescrita por plataforma.
UIFlutterJanela, canvas, chat, barra lateral, formulários, gesto e animação.Não guarda regra de negócio: mostra o estado do core e manda intenções.

Decisões

#DecisãoDe onde veio
1Rust fica com core e driver; Flutter fica com a UI.Pedido inicial
2Sem gerador de código na ponte entre Rust e Dart — o flutter_rust_bridge está fora.Debate sobre a fronteira UI ↔ core
3O emulador de terminal é o libghostty-vt, o motor oficial do Ghostty, usado direto — sem widget nem binding de terceiro. Ele fica num componente próprio, “terminal”, ao lado de driver e core: o core continua sem dependência nativa e fala com o terminal por uma interface. A pintura e a entrada no Flutter são escritas por nós.Debate sobre o emulador de terminal
4A arquitetura é modular em todos os componentes — driver, core, terminal e UI. O desenho dos módulos de cada uma ainda será debatido.Debate sobre o emulador de terminal
5O pty fica no driver. O componente terminal é só o emulador: recebe bytes, mantém a tela e não tem código por plataforma.Debate sobre o emulador de terminal
6Core tem todas as lógicas do app, incluindo a comunicação por socket, arquivos, git e rede. Driver é só o que dá acesso a coisas do sistema operacional que podem diferir por plataforma, como o pty. Teste prático: se o código precisa de um cfg por sistema, é driver; se não, é core.Debate sobre core × driver
7As interfaces pertencem ao core. Para tudo que está no driver ou no componente terminal, o core define a interface com o formato do que ele precisa (não o da API do sistema), e o driver a implementa por plataforma. O core não conhece o driver; uma peça fina no topo monta os dois. Só há interface para o que varia: arquivos, git, rede e relógio o core usa direto.Debate sobre core × driver
8A UI fala com o core pelo socket, como mais um cliente — sem bridge e sem gerador de código. O protocolo é por mensagens (comando, resposta, evento empurrado) e não depende do transporte: hoje socket local, e o mesmo protocolo deve servir a um app do Egeon lançado à parte.Debate sobre a estrutura da UI
9Haverá um app mobile que dá acesso remoto ao Egeon do usuário. Não é o primeiro passo, mas o protocolo e a estrutura da UI já nascem servindo a ele: mesmas mensagens, mesmo código de repository, outra conexão.Debate sobre a estrutura da UI
10Todo código Rust segue o padrão da seção “Padrão do Rust: core e driver”, tirado das práticas da comunidade: workspace plano, core por features com interfaces em ports/, um dono do estado, erros tipados, unsafe só no driver e no terminal. Macros derive são aceitas no Rust.Pesquisa na comunidade Rust
11Sem transição. A migração é de ponta a ponta, nesta branch. O app Swift vai para uma pasta provisória e serve só de referência para o porte, até ser removido.Você
12Porte fiel. Nada é corrigido no Swift e o comportamento é portado como está — inclusive a fila de injeção e os pedidos de permissão só em memória.Você
13O core Rust é um executável próprio, que o app Flutter lança como processo filho ao abrir; o usuário só abre o app. O mesmo executável roda sem janela, o que permite testar core e driver por curl. Não há FFI entre Dart e Rust. A conferir no primeiro teste: o microfone continuar atribuído ao app.Delegado; escolhido para facilitar os testes
14O libghostty-vt entra como biblioteca já compilada, distribuída pelo projeto Ghostty, com versão fixa e conferida por checksum. Compilar do fonte (exige Zig) fica como plano B. Conferido no primeiro build: o Ghostty publica ghostty-vt-1.0.1.xcframework.zip (tag vt-1.0.1, MIT, .a estático universal arm64+x86_64, só libSystem); o build.rs fixa e confere o sha256 do zip e do .a; EGEON_GHOSTTY_VT_DIR aponta um .a próprio. Não há binário oficial para Linux: lá vale o plano B. A assinatura minisign não é conferida, só o sha256.Delegado
15O egeon vira binário Rust, incluindo os ganchos (egeon hook <evento>). Hoje cada gancho dispara bash, curl e python3; passa a ser um processo nativo só.Delegado; escolhido por desempenho
16O canal da UI é um upgrade no mesmo socket: a UI faz GET /ui com Upgrade: egeon-ndjson, recebe 101 e a conexão passa a levar uma mensagem JSON por linha — comando {"id","cmd",…}, resposta {"re":id,…} e evento {"topic",…}. As rotas HTTP de hoje continuam para o egeon e o curl. Se o volume do terminal não couber, só o stream das linhas muda de formato.Você, na partida da implementação
17Até o corte, o app novo grava em ~/.egeon-next, com os mesmos formatos de ~/.egeon; EGEON_HOME sobrescreve, para teste. O ~/.egeon do Egeon estável não é tocado.Você, na partida da implementação
18O primeiro marco é um corte vertical: um terminal de verdade de ponta a ponta — core com ator único e socket, driver macOS (pty e conexão local), terminal sobre libghostty-vt, egeon-app sem janela conferido por curl, e a UI lançando o core e pintando o terminal — com a medida do volume do terminal no socket. Persistência, bancadas e chat vêm nos marcos seguintes.Delegado
19O app Flutter roda sem sandbox do macOS (com.apple.security.app-sandbox falso nos .entitlements do Runner): ele lança o egeon-app como filho, abre o socket em ~/.egeon-next e os agentes leem e gravam fora do contêiner. O app Swift de hoje também não tem sandbox.Porte fiel (decisão 12), apontado na revisão da UI
20Colar é comando do core. O canal da UI ganha paste {node,text}: o core embrulha o texto em \e[200~…\e[201~ quando o programa ligou o modo 2004 (bracketed paste), como faz o SwiftTerm hoje, e manda cru quando não ligou. A UI não conhece o modo da tela; quem sabe é o terminal, pela interface de tela.Delegado; porte fiel apontado na verificação do marco 1
21O core lançado pela UI morre com ela. A UI lança o egeon-app com o stdin ligado a um cano dela; quando o cano fecha (⌘Q, queda ou kill -9 da UI), o core encerra os terminais e sai — como hoje fechar o app mata tudo. Um core que a UI encontrou já de pé (lançado à parte, sem janela) não é encerrado por ela.Delegado; porte fiel apontado na verificação do marco 1
22O HTTP do socket segue o ControlSocket.swift (cabeçalho sem dois-pontos ignorado, Content-Length ausente ou não numérico usa o corpo que chegou, alvo absoluto aceito), com três divergências: teto de 64 MiB no corpo, com 413 — no Swift um Content-Length absurdo faz o app crescer em memória sem limite; GET /ui com upgrade não tem corpo — o que vem depois do cabeçalho já é do canal; Content-Length: sem valor ou negativo vale como ausente — no Swift derrubava o app (índice fora do split), e o core não pode cair (regra de código 9).Delegado; levantado na verificação do marco 1
23Flavor sem bundle. O core não tem bundle id: o sabor sai de EGEON_FLAVOR=dev, que a UI acende a partir do bundle id dela; ausente, vale o estável, como o Swift sem bundle. Pasta: EGEON_HOME > ~/.egeon-next (estável) ou ~/.egeon-next-dev (dev) até o corte; depois, ~/.egeon e ~/.egeon-dev. Até o corte, o identificador do sabor (o EGEON_DECK marcado nos processos) é egeon-next/egeon-next-dev: com egeon, o reaper do Egeon estável tomaria os terminais do app novo como órfãos e os mataria em 1 h; o classify passa a reconhecer egeon-app como outro Egeon, além de EgeonDeck. O ~/egeon.log não é portado agora: o core loga no stderr.Delegado; desenho do core no US-102
24Contrato /ui de organização. Tópicos workspaces (árvore workspace → projeto → bancada, órfãs e a faixa de abas dentro) e workbench/<id>/nodes (nós com frame, tipo, agente e o id da tela, e as arestas), sempre o estado inteiro do item, sem delta. Comandos que mudam algo respondem só {re,ok,id}; o estado novo chega pelo tópico. Chaves em snake_case; a UI identifica bancada pelo id, o nome só vai no endereço. Comandos: criar/remover/abrir/fechar/ativar bancada, move igual ao /move do Swift, move_tab, criar/remover/mover nó, set_workbench, set_node, link/unlink/set_edge, workspace e projeto. Também no tópico: bancadas Ativas e a atividade por bancada; e a pergunta plan_move → {lands}, sem aplicar, para o realce do arrasto — a regra do SidebarDrop fica no core. O plan_remove_workbench traz, por worktree, as linhas do alerta de perdas (o lossLines do Swift). Zoom e pan ficam fora (só UI).Delegado; desenho do core, acréscimos do maestro
25O egeon-cli usa egeon_core::commons::paths, além do protocol: o caminho do socket e da pasta tem de ser exatamente o do core, e duplicá-lo abriria espaço para divergência. Exceção à tabela do padrão Rust, que previa só o protocolo. Débito anotado: o cliente do egeon usa std::os::unix e só roda em Unix; Windows pede named pipe.Delegado; revisão do US-106
26Terminal completo no canal /ui. Comandos scroll, pointer (o core conta os cliques pelo tempo da UI e manda ao pty o que o modo de mouse pedir, ou vira seleção e rolagem), select_all e copy; o quadro ganha scrollbar e a seleção por linha; efeitos bell, clipboard (OSC 52 gravando) e clipboard_request, a que a UI responde com clipboard_reply — a área de transferência nunca vai ao core de antemão. Título (OSC 0/2) e OSC 7 ficam de fora, como no Swift.Delegado; terminal e core, porte do SwiftTerm
27Cliente HTTPS do core: reqwest com rustls, sobre o tokio. O feed de atualização e os nomes dos arquivos são parâmetro; o padrão provisório do app novo é o mesmo repositório com EgeonDeckNext.zip/.sig e o bundle id dev.duckcoder.egeondeck.next. Nada é publicado até haver processo de release.Delegado; provisório, pergunta aberta
28Nó web: platform view nativa (WKWebView) sobreposta na posição do card quando o zoom é 100% e o canvas está parado; em pan, zoom ou fora de 100%, mostra a última captura da página como imagem e volta ao vivo quando para. Cursor do cabeçalho do card: mão aberta (grab), como o código do Swift — diverge do texto do ADR-048, que fala em seta.Delegado; provisório até você ver (pergunta 6)
29Chat no canal /ui. Tópico chat/<id da bancada>, uma assinatura por bancada, com rev e as operações do diff de blocos (reset na assinatura e em rev perdido); comandos chat_snapshot, chat_step, chat_more, chat_clear (arquiva) e chat_send{to,text,quote?}; participantes e bandeja de permissão como operações próprias no mesmo tópico, respondidas com permission_answer. O bloco de código traz os spans do realce de sintaxe, calculados no core; @menção e /slash do composer vêm da consulta chat_complete{workbench,text,caret} → {items,range}; permission_answer aceita answers de várias perguntas, como o /permission/answer. Regras com estado de formulário (esforço, onde soltar na barra lateral) ficam no core; a UI só mostra o que vier e devolve o gesto.Delegado; desenho do core e do chat-rs
30A thread principal do egeon-app gira o run loop do sistema (no macOS, CFRunLoopRun), oferecido pelo driver; o tokio roda nas outras threads. Sem isso, NSWorkspace.runningApplications fica congelado e notificações não saem, como num app AppKit sem loop principal.Delegado; revisão do US-303
31Nós de agente, fila e web no canal /ui. Tópico node/<bancada>/<nó>, separado do de nós da bancada para o medidor de contexto e a fila não reenviarem a bancada inteira. Agente: catálogo de modelos como o ModelRow do Swift, o dial de esforço com estado no core (effort_move, effort_toggle_auto, effort_settle — a UI só guarda o tempo de assentar), ultracode, contexto e node_clear. Fila: o /queue do Swift em comandos, itens com a conversa de cada um. Web: web_navigate (o core normaliza o digitado), web_navigated e web_set_profile; voltar, avançar e recarregar ficam na webview. O /queue?open=&draft= vira efeito no tópico do nó.Delegado; desenho do core com o ui-canvas
32Desvios deliberados do Swift: o script de troca do app roda em grupo de processos próprio (o killpg do encerramento do core não o mata); os apps abertos vêm do lsappinfo, não do NSWorkspace; o histórico do terminal tem teto de 500 + 48000/colunas linhas, porque o Ghostty poda por página (medido ≥ 500 linhas de 10 a 500 colunas); com duas instâncias do mesmo app, a reivindicação da primeira não é apagada pela segunda. Todo nó recebe EGEON_HOME e EGEON_FLAVOR no ambiente, que o Swift não punha: o egeon e os ganchos do filho precisam achar a pasta e o sabor do app novo (decisão 23), e não podem cair no ~/.egeon do estável. O BranchName só recusa nome vazio, como o Swift: o nome que o git check-ref-format recusa chega ao git e volta com o erro dele (25 de 43 nomes testados) — validar antes mudaria a mensagem que o usuário vê. Lacunas conhecidas: o Ghostty 1.0.1 não expõe a captura do shift (XTSHIFTESCAPE), então shift sempre passa por cima do mouse do programa.Delegado; revisões do marco 2
33(1) A UI avisa o foco: ui_focus{app_active, node?} — o NSApp.isActive e o first responder do Swift, de que o envio e a notificação precisam. (2) O nó web usa um plugin nativo mínimo no runner do Flutter (platform view com WKWebView e canal egeon/web), porque o pacote webview_flutter não isola cookies por perfil nem tira captura; o app novo passa a exigir macOS 14, como o Swift. (3) Regra de negócio nunca fica duplicada na UI: o core manda o resultado pronto (onde soltar, dial de esforço, needs_attention) e a UI só desenha.Delegado
34(1) Tópico app no canal /ui: estado da atualização e efeitos update_prompt, update_message, terminate e show_processes (o show=1 do /processes). (2) Hora local: o core usa o fuso do sistema direto, por crate portátil, sem interface no driver — trilha e chat gravam a hora local, como o Swift.Delegado
35As rotas HTTP que dependem da tela (/layout, /sidebar, /geometry, /shot) ficam no socket como hoje: o core repassa à UI um ui_request{id,route,params} no tópico app e devolve ao cliente o ui_reply dela; sem UI, responde como o Swift sem janela. Desvios: o nó é reapontado para a worktree mesmo com a bancada fechada (o Swift exigia aberta); EGEON_NO_UPDATE_CHECK=1 desliga a consulta ao feed no arranque, para teste.Delegado
36Até o corte, o app novo não grava skills nas pastas de config do Claude do usuário (~/.claude*); a confiança da pasta (hasTrustDialogAccepted no .claude.json) é gravada como no Swift, por pedido do Julio em 2026-11-18, para o diálogo "trust this folder" nunca aparecer: além da herança do Swift (worktree e multi-projeto), a pasta de todo nó Claude é aceita ao subir, inclusive checkout principal nunca aceito — o que também aplica sem perguntar as permissões do .claude/settings.local.json da pasta: o Egeon estável instala as mesmas skills ali e os dois brigariam. Grava só no CLAUDE_CONFIG_DIR que ele mesmo aponta; os ganchos ficam em <EGEON_HOME>/claude-hooks.json. Depois do corte, vale o comportamento do Swift.Delegado
37Mais contratos no canal /ui, no estilo da 24, com tudo pronto para a tela: templates, worktree_info, worktree_plan (o BranchPlan do ADR-018, sem criar nada) e worktree{destination,template?}; tópico workbench/<id>/usage com a pastilha e o painel de consumo com os textos do Swift; processes, processes_reap e processes_kill, com dry_run devolvendo o texto da confirmação — o “Encerrar órfãos” da janela leva todos os órfãos, como o Swift, diferente da rota /processes/reap. O app do Flutter leva egeon-app e egeon em Contents/MacOS, compilados por uma fase do Xcode (rust/scripts/embed_core.sh). A janela Processos vira painel flutuante e não modal na janela do app, uma instância só e com foco próprio (o Swift abria janela própria; modal travava o resto do app); várias janelas no Flutter ficam para depois.Delegado
38O core grava o próprio log em <EGEON_HOME>/egeon.log, com rotação simples, além do stderr: aberto pelo Finder, o stderr do processo filho não vai a lugar nenhum. É o ~/egeon.log do Swift, por sabor, como o FlavorTests.testLogsAreSeparate pede.Delegado; verificação final do arquiteto
39Regras que a verificação final tirou da UI: o nó que nasce sem frame recebe o frame do defaultFrames do Swift no core, gravado na primeira vez, com o tamanho do canvas vindo em ui_focus.window (sem ele, 900×600); o core diz quem pode ligar com quem (linkable) e recusa o resto; o estado da fila vem pronto (destino, pendentes, resumo, trava, imagens aceitas); a atividade vem somada por workspace e projeto; a tela “sem acesso” tem access na bancada e os comandos access_open_settings e access_ask_again. Bancada nova a partir de worktree aceita pasta sem bancada de origem; chat_new_queue cria fila pelo chat.Delegado; verificação final do arquiteto
40O catálogo de modelos do Claude é lido do binário do CLI em blocos, com memória constante: o Swift usa mmap, que no core exigiria unsafe; copiar o binário inteiro (≈ 340 MB) para a memória a cada leitura não é aceitável. Os testes nunca leem o claude real da máquina.Delegado; diagnóstico de memória pedido por você
41Desenvolvimento como no Swift, adaptado: dois apps lado a lado, montados por ui/scripts/make.sh [debug|release] [stable|dev] e derrubados e reabertos por ui/scripts/dev.sh (dev por padrão). O dev é EgeonDeck Next Dev.app, dev.duckcoder.egeondeck.next.dev, com o ícone dev do Swift, e guarda tudo em ~/.egeon-next-dev. Quem diz ao app que ele é o dev é o EGEON_FLAVOR=dev no LSEnvironment do bundle; a UI escolhe a pasta por ele e o repassa ao core. O app é encerrado com SIGTERM, sem osascript, porque quem grava o estado é o core, que sai em ordem quando a UI morre.Pedido por você («o mesmo setup do Swift, adaptado»); detalhes delegados
42Injeção de dependências da UI com GetIt, atrás de um wrap em core/adapters/injector.dart (só ele importa a lib). Cada feature tem o seu módulo em features/<f>/di/, com todas as injeções dela, separando os repositórios reais do domínio (usecases e cubits) para os testes registrarem os falsos; o global em core/di/ registra o que é do core do front e chama todos os módulos. Quase tudo é factory; o que é de uma bancada ou de um nó recebe o id como parâmetro. Únicos só o socket, o lançador, o feed da organização, a conexão, o repositório do canvas (cache dos frames) e os registros da casca. A página cria o cubit com BlocProvider(create: …), que o fecha ao sair.Pedido por você; detalhes delegados
43Estado de tela é do cubit, num <x>_state.dart que é part of dele, nunca em domain/entities (entidade é o que vem do core Rust). Fases que se excluem são sealed class, uma subclasse por fase; campo que vale em todas as fases fica na base, o de só algumas na subclasse. Cada feature tem os seus erros em domain/errors (sealed: recusa do core, com o texto dele, e conexão caída); o repositório converte a falha do socket, o cubit trata só o erro da feature.Pedido por você; detalhes delegados
44Design system Graphite no lugar da UI provisória. O tema escuro Graphite do design system Egeon substitui o tema antigo de ui/lib/theme/ (que sai módulo a módulo, nas etapas do redesign); nada da UI provisória é reaproveitado. Fontes Noto Sans e JetBrains Mono (.ttf variáveis, normal e itálico) embutidas no app, sem google_fonts, para abrir offline. Vidro (blur 20, saturação 130%) só no que flutua. Ícones do próprio DS, na grade de 16 com traço 1.5 (os caminhos do componente Icon do DS e os desenhados nas telas do canvas, desenhados por um CustomPainter sem pacote de ícones; a rota do pacote Lucide foi trocada por esta, aceita pelo maestro em 2026-11-19). O Dart do tema é escrito à mão e preso ao tokens.json por teste de paridade. O Material vem de material_ui, porque package:flutter/material.dart está descontinuado no Flutter 3.50. O terminal usa só as cores ANSI do DS: o emulador é o libghostty no Rust, sem o pacote xterm.Julio, em 2026-11-19
45Moldura da janela (E2). Janela sem barra de título pelo próprio runner: MainFlutterWindow.swift tira o título e deixa o conteúdo ir até o topo, e o canal egeon/window ganha startDrag e toggleZoom (a faixa de cima de 44 arrasta e maximiza no duplo clique); sem window_manager (0.7 traz o nativeapi, pesado) nem macos_window_utils, e sem mexer em Info.plist. Linux e Windows desenham os próprios botões de janela quando chegarem. Voltar e avançar (⌘[ ⌘]) entre bancadas é só da UI: o core não guarda por onde se passou (nem o Swift), então o histórico fica num cubit da casca, até 50 bancadas, pulando as sem aba. Cor da bancada: o core segue gravando os 24 nomes antigos; a UI lê cada um como a identidade de matiz mais próximo e grava um nome antigo fixo por identidade (BenchIdentity), provisório até o Julio decidir a paleta. Atalhos: ⌘[ voltar e ⌘] avançar (antes eram aba anterior e seguinte; as abas ficam em ⌘← ⌘→).Delegado ao dev na E2; para o Julio rever
46Trilho e gaveta de bancadas (E2, H3, H4, H6, H7). A barra lateral deixa de flutuar: no lugar fica o trilho de bancadas (as abas abertas, com o estado de cada uma) e a barra atual passa a morar na gaveta, que abre do trilho por cima do canvas, ao lado no chat, sem fixar: só abre e fecha. Camadas fixas (ShellLayers): lugar da barra de ações, do consumo, dos pedidos de permissão e do composer, e o aviso passageiro sobe por cima do que o pé da moldura já ocupa. ⌘K abre a gaveta (a busca é da E3). Descartado — fixar a gaveta: sem fixar, a gaveta só abre e fecha — Julio; logo não há o que persistir. Também em aberto: o plano H7 lista ⌘1–⌘4 como ferramentas do canvas, mas hoje ⌘1–⌘9 vão à aba de número n (porte fiel); decidir com o Julio antes da E4.aberta só no ⌘1–⌘4 · fixar/persistir: descartado
47“Parada há X” e paradas recolhíveis na barra lateral (v3). A v3 escreve, em cada bancada parada, “Parada há 3 d”, agrupa no fim do projeto “N paradas há mais de 3 dias” (recolhível) e tem o filtro “Recolher paradas há mais de…” (24 h, 3 dias, 1 semana, nunca). O Swift só separa, na aba Ativas, o que rodou nas últimas 24 h do resto (ActiveWorkbenches.swift). O que muda no fio: o core já guarda o instante em clock.last_active (porte do WorkbenchClock.lastActive); a proposta é expô-lo no retrato da bancada (last_active em WorkbenchView, tópico workspaces), em ISO 8601 como o resto. A UI formata o “há X” e agrupa; o recolher fica na árvore, não no core. Por quê: sem o instante a UI só sabe “parada” ou “não”, e não há como escrever “há X” sem inventar. Risco: baixo para o dado (campo opcional, clientes antigos ignoram); o agrupamento/recolher é desenho novo, e “parada” hoje vem do resumo de atividade (nada trabalhando nem esperando), não de last_active — as duas noções têm de coincidir.aberta · para o Julio
48Flag maestro no participante do chat (v3). Na v3 o maestro é sand fixo em todo lugar: no card, na coluna de participantes e no “Para maestro” do composer. O chat do Swift só colore por hash do id (ChatParticipant.swift:16,55). O caminho de um caractere

Do processo até a tela, e da tecla de volta, passando por todos os componentes:

saída   processo ─▶ pty (driver) ─bytes─▶ core ─bytes─▶ tela (terminal) ─linhas alteradas─▶ core ─mensagem─▶ UI pinta
entrada UI captura tecla ─mensagem─▶ core ─▶ terminal codifica a tecla ─bytes─▶ core ─▶ pty (driver) ─▶ processo

O core fica no meio porque só ele conhece as duas interfaces. É também por isso que ele sabe o instante do último byte (os tempos da injeção) e lê o texto da tela (egeon peek, marcador de CLI sem gancho) sem depender da UI.

Ainda fora do desenho

  • Nó web — precisa de view nativa (WKWebView no macOS); não foi discutido onde entra.
  • Janela, menus nativos e drop de arquivo — parte nativa do lado do Flutter; não discutido.
  • Módulos internos de cada componente — a decisão 4 diz que são modulares; o recorte ainda será debatido.

Por dentro do driver

O padrão da biblioteca padrão do Rust e de crates como mio e winit: um crate só, um módulo por capacidade, e dentro dele um arquivo por plataforma escolhido na compilação. (A organização desses crates eu cito de memória; não conferi nesta pesquisa.)

egeon-driver/src/
├─ lib.rs
├─ pty/          mod.rs (implementa o trait do core) · unix.rs · windows.rs
├─ procs/        mod.rs · macos.rs · linux.rs · windows.rs
├─ local_conn/   mod.rs · unix.rs · windows.rs
├─ notifier/     mod.rs · macos.rs · …
└─ folders/      mod.rs · macos.rs          (TCC só existe no macOS)

Muda uma coisa que eu tinha dito antes: em vez de um crate por plataforma, um crate com arquivos por plataforma. macOS e Linux compartilham quase tudo de pty e socket; separar por crate duplicaria esse código. Enquanto só houver macOS, cada módulo tem um arquivo.

Em debate

Pontos ligados a decisões já tomadas que ainda pedem medida ou cuidado.

TemaOnde paramos
Custo do socket sem geradorModelos Dart e fromJson à mão; erro de campo só aparece em execução, o que pede testes de contrato com exemplos gravados pelo Rust.
Volume do terminalSe o socket unix aguenta o volume dos terminais. Medido no marco 1 (M4 Pro, egeon-app em release, libghostty-vt 1.0.1, terminal 120×40, cliente do /ui em Python lendo NDJSON como a UI lê): seq 1 500000 leva 421 ms sem ninguém assinando a tela e 436 ms assinada, em 4.429 quadros e 10,4 MB de NDJSON; cat de 50 MB leva 620 ms sem assinatura e 450 ms assinada, em 2.642 quadros e 13 MB. Tecla até o quadro com o eco: p50 0,9 ms e máximo 1,4 ms com o terminal ocioso; p50 1,4 ms e máximo 1,7 ms com outro terminal despejando yes para outro cliente. Conclusão: aguenta. Quem limita é o pty, não o socket: assinar a tela não muda o tempo do comando, porque o ator junta num quadro só a saída que chega enquanto ele trabalha. FFI cru não é preciso. Fica um ponto para a UI: sob carga chegam milhares de quadros por segundo (~25 MB/s de JSON). Se o Dart sentir, a saída é limitar no core a taxa de quadros por cliente (ex.: um a cada 8 ms, juntando os deltas), sem mudar o formato.
