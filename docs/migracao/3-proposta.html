Proposta

O que já foi decidido sobre a migração, o que está em debate e o que ainda não foi discutido. Cresce conforme a conversa; nada entra como decidido sem passar por você.

Decidido

Premissa

CamadaLinguagemO que éRegra
CORERustToda a lógica do app: modelos, estado, regras, persistência, git, rede, protocolo e rotas do socket.Só usa o que é igual em qualquer plataforma. Testável com cargo test, sem app aberto.
DRIVERRustAcesso ao sistema que difere por plataforma: pty, processos e sinais, conexão local com pid do par, TCC, notificação, troca do app na atualização.Implementa traits que o core define. É a única parte reescrita por plataforma.
UIFlutterJanela, canvas, chat, barra lateral, formulários, gesto e animação.Não guarda regra de negócio: mostra o estado do core e manda intenções.

Decisões

#DecisãoDe onde veio
1Rust fica com core e driver; Flutter fica com a UI.Pedido inicial
2Sem gerador de código na ponte entre Rust e Dart — o flutter_rust_bridge está fora.Debate sobre a fronteira UI ↔ core
3O emulador de terminal é o libghostty-vt, o motor oficial do Ghostty, usado direto — sem widget nem binding de terceiro. Ele fica num componente próprio, “terminal”, ao lado de driver e core: o core continua sem dependência nativa e fala com o terminal por uma interface. A pintura e a entrada no Flutter são escritas por nós.Debate sobre o emulador de terminal
4A arquitetura é modular em todos os componentes — driver, core, terminal e UI. O desenho dos módulos de cada uma ainda será debatido.Debate sobre o emulador de terminal
5O pty fica no driver. O componente terminal é só o emulador: recebe bytes, mantém a tela e não tem código por plataforma.Debate sobre o emulador de terminal
6Core tem todas as lógicas do app, incluindo a comunicação por socket, arquivos, git e rede. Driver é só o que dá acesso a coisas do sistema operacional que podem diferir por plataforma, como o pty. Teste prático: se o código precisa de um cfg por sistema, é driver; se não, é core.Debate sobre core × driver
7As interfaces pertencem ao core. Para tudo que está no driver ou no componente terminal, o core define a interface com o formato do que ele precisa (não o da API do sistema), e o driver a implementa por plataforma. O core não conhece o driver; uma peça fina no topo monta os dois. Só há interface para o que varia: arquivos, git, rede e relógio o core usa direto.Debate sobre core × driver
8A UI fala com o core pelo socket, como mais um cliente — sem bridge e sem gerador de código. O protocolo é por mensagens (comando, resposta, evento empurrado) e não depende do transporte: hoje socket local, e o mesmo protocolo deve servir a um app do Egeon lançado à parte.Debate sobre a estrutura da UI
9Haverá um app mobile que dá acesso remoto ao Egeon do usuário. Não é o primeiro passo, mas o protocolo e a estrutura da UI já nascem servindo a ele: mesmas mensagens, mesmo código de repository, outra conexão.Debate sobre a estrutura da UI

O caminho de um caractere

Do processo até a tela, e da tecla de volta, passando por todos os componentes:

saída   processo ─▶ pty (driver) ─bytes─▶ core ─bytes─▶ tela (terminal) ─linhas alteradas─▶ core ─mensagem─▶ UI pinta
entrada UI captura tecla ─mensagem─▶ core ─▶ terminal codifica a tecla ─bytes─▶ core ─▶ pty (driver) ─▶ processo

O core fica no meio porque só ele conhece as duas interfaces. É também por isso que ele sabe o instante do último byte (os tempos da injeção) e lê o texto da tela (egeon peek, marcador de CLI sem gancho) sem depender da UI.

Ainda fora do desenho

  • Nó web — precisa de view nativa (WKWebView no macOS); não foi discutido onde entra.
  • Janela, menus nativos e drop de arquivo — parte nativa do lado do Flutter; não discutido.
  • Módulos internos de cada componente — a decisão 4 diz que são modulares; o recorte ainda será debatido.

Estrutura da UI

definida por você — a organização do front em Flutter. O encaixe de cada peça do Egeon nela ainda está em aberto, no fim da seção.

lib/
├─ features/
│  └─ <feature>/
│     ├─ presentation/
│     │  ├─ cubit/        orquestra o estado da tela a partir do que o usecase retorna
│     │  ├─ page/         só compõe widgets; quase nada solto
│     │  └─ widgets/      os componentes da página
│     └─ domain/
│        ├─ entities/     os modelos, com fromMap e toMap
│        ├─ repository/   faz as consultas pelo socket
│        └─ usecase/      consulta os repositories para montar algo específico da tela
├─ core/
│  ├─ adapters/           wrap de toda lib externa — menos as de UI, que vão para commons
│  ├─ domain/             mesma estrutura do domain das features, para o que é usado em mais de um módulo
│  └─ cubits/             cubits globais (raro: costuma bastar um AppCubit na raiz)
├─ commons/
│  ├─ widgets/            widgets compartilhados: o design system ou adaptação de lib externa de UI
│  ├─ utils/              utilitários básicos (datas, formatação)
│  └─ forms/              validators e máscaras
└─ theme/                 cores do app, temas, decorations, fontes com seus pesos

Eventos empurrados pelo core

decidido

QuemPapel
Core RustManda o estado inteiro do item a cada mudança, não a diferença. A assinatura é por tópico, numa conexão só. Se a conexão cair, a UI assina de novo e recebe o estado atual
repositoryFuture para consulta e comando; Stream para o que o core empurra
usecaseRepassa o stream, ou combina quando a tela junta mais de uma fonte
cubitDono da assinatura: abre ao nascer, emite estado a cada evento, cancela no close(). A vida da assinatura é a vida da tela
GranularidadeUm cubit por item (card de nó, linha da barra lateral), não um por tela — para o tique de badges e relógios não reconstruir tudo
Exceção: terminalO widget escuta o stream das linhas direto e repinta só o que mudou; o cubit cuida do resto (título, tamanho, se está vivo)
Exceção: chatO core manda a diferença de blocos (removidos, inseridos, alterados), porque a thread é longa

rascunho — falta a sua revisão

As 53 funcionalidades de hoje, cada uma dividida no que seria core, driver e UI. Um traço significa que a camada não participa. A divisão segue a decisão 6: o core tem toda a lógica, inclusive arquivos, git, rede e o protocolo do socket; o driver tem só o acesso ao sistema que muda de uma plataforma para outra; a UI mostra e captura gesto.

Cortes que não são óbvios

Onde a linha poderia passar em outro lugar. São os pontos a discutir antes de dar este mapa como decidido.

#CorteComo está acimaAlternativa
1Emulador de terminal decididoNum componente próprio, “terminal”, com libghostty-vt; a UI só pintaDescartadas: emulador em Dart (xterm e forks, flterm) e SwiftTerm embutido
2Montagem do chatTurnos → blocos e o diff de blocos no core; a UI só mede e listaO core entrega turnos e a UI monta os blocos. Menos tráfego na fronteira, mais regra na UI
3Estado de tela (passos abertos, foco do chat, ferramenta armada, modo)No core, para as rotas de verificação enxergaremNa UI, por ser efêmero. Aí as rotas /chat e /layout teriam de perguntar à UI
4Zoom e pan do canvasSó na UI; o core guarda apenas os frames dos cardsGuardar zoom e posição por bancada no core, para voltar onde estava
5Geometria das arestasRota e hit-test no core (são geometria pura e têm teste)Na UI, junto do desenho — evita atravessar a fronteira a cada movimento de card
6Notificação, som e nó webNotificação e som no driver; nó web na UI (nativo)Tudo que é API do macOS no runner Swift do Flutter, e o driver Rust fica só com pty, processos, arquivos e rede
7Persistência decididoO core lê e grava direto—
8Relógio e timers decididoNo core; para testar os tempos da injeção, o relógio é um parâmetro dentro do próprio core—

Em debate

Pontos ligados a decisões já tomadas que ainda pedem medida ou cuidado.

TemaOnde paramos

Perguntas abertas

#PerguntaPor que importa
1Qual é o motivo da migração?Se não é para rodar em Linux ou Windows, o driver pode ser só macOS e o trabalho cai. Não há ADR nem motivo registrado.
2A restrição a gerador de código vale também dentro do Dart?Gerência de estado e modelos imutáveis no Flutter costumam puxar gerador (freezed, json_serializable, riverpod_generator).
3Processo único ou core como daemon?Microfone (TCC), identidade por pid e árvore de processos dependem de o app ser o pai do pty. Daemon reabre o ADR-010.
4App novo em paralelo, ou Rust por baixo do app Swift primeiro?Define se existe uma ponte Swift ↔ Rust temporária e por quanto tempo os dois apps convivem.
5Como o libghostty-vt entra no build: biblioteca já compilada do projeto, ou compilar do fonte (exige Zig)?Define o que precisa estar instalado para compilar o Egeon e como a biblioteca vai dentro do bundle.
10Como o core Rust é ligado quando o app abre?Como biblioteca dentro do app (uma função chamada pelo Dart, escrita à mão) ou como processo filho lançado pelo Flutter (nenhum FFI).
11adiada Acesso remoto: como o celular alcança o Egeon e como se autentica?Socket unix só funciona na mesma máquina, e a identidade de hoje vem do pid de quem conecta. Pela rede é preciso outro transporte, pareamento do aparelho e autenticação; fora da rede local, também um caminho até o computador (relay ou VPN).
12adiada O Egeon precisa responder ao celular com a janela fechada?Se sim, o core tem de rodar sem a UI de desktop, o que pesa na pergunta 10 e reabre “processo único ou daemon” (pergunta 3).
6O que fazer com o nó web sob zoom?WKWebView embutido não acompanha a transformação do canvas.
7Fila de injeção e pedidos de permissão continuam só em memória?Hoje somem no restart.
8Bugs achados no levantamento: corrigir no Swift antes, ou só no porte?Define se o Rust replica o comportamento atual ou já nasce diferente.
9Vidro do macOS 26: aceitar a perda visual?Não há equivalente no Flutter.
