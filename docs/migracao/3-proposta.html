Proposta

O que já foi decidido sobre a migração, o que está em debate e o que ainda não foi discutido. Cresce conforme a conversa; nada entra como decidido sem passar por você.

Decidido

Premissa

CamadaLinguagemO que éRegra
CORERustDomínio puro: modelos, stores, parsing, guardas, planejador do maestro, preços, diff, estado das bancadas.Não toca SO nem UI. Testável com cargo test, sem app aberto.
DRIVERRustO que fala com o macOS: pty, processos, socket de controle, sistema de arquivos, git, Keychain, rede.Implementa traits que o core define. É a única parte que muda por plataforma.
UIFlutterJanela, canvas, chat, barra lateral, formulários, gesto e animação.Não guarda regra de negócio: mostra o estado do core e manda intenções.

Decisões

#DecisãoDe onde veio
1Rust fica com core e driver; Flutter fica com a UI.Pedido inicial
2Sem gerador de código na ponte entre Rust e Dart — o flutter_rust_bridge está fora.Debate sobre a fronteira UI ↔ core
3O terminal começa com um emulador em Dart: fica do lado do Flutter, isolado atrás de uma interface própria para poder ser trocado sem mexer no resto. O pacote ainda não está escolhido. A forma dessa segregação entra no debate da arquitetura do Flutter.Debate sobre o emulador de terminal

Cortes que não são óbvios

Onde a linha poderia passar em outro lugar. São os pontos a discutir antes de dar este mapa como decidido.

#CorteComo está acimaAlternativa
1Emulador de terminal decididoNa UI, com emulador em Dart, isolado atrás de uma interfaceEmulador em Rust no driver. Fica como troca possível depois, se a leitura da tela pelo core ou o desempenho incomodarem
2Montagem do chatTurnos → blocos e o diff de blocos no core; a UI só mede e listaO core entrega turnos e a UI monta os blocos. Menos tráfego na fronteira, mais regra na UI
3Estado de tela (passos abertos, foco do chat, ferramenta armada, modo)No core, para as rotas de verificação enxergaremNa UI, por ser efêmero. Aí as rotas /chat e /layout teriam de perguntar à UI
4Zoom e pan do canvasSó na UI; o core guarda apenas os frames dos cardsGuardar zoom e posição por bancada no core, para voltar onde estava
5Geometria das arestasRota e hit-test no core (são geometria pura e têm teste)Na UI, junto do desenho — evita atravessar a fronteira a cada movimento de card
6Notificação, som e nó webNotificação e som no driver; nó web na UI (nativo)Tudo que é API do macOS no runner Swift do Flutter, e o driver Rust fica só com pty, processos, arquivos e rede
7PersistênciaO core decide o formato; o driver lê e gravaO core lê e grava direto com std::fs, e o driver fica só com o que varia por plataforma. Menos traits, core menos puro
8Relógio e timersNo driver, injetado no core (para testar os tempos da injeção)O core usa o relógio do sistema direto

Em debate

Encaminhado na conversa, ainda sem o seu "sim".

TemaOnde paramos
Core ↔ driverCrates Rust no mesmo processo: o core define traits, o driver implementa, e eventos voltam por canal em memória. Sem socket entre os dois.
UI ↔ coreUm protocolo só, por mensagens: a UI vira mais um cliente do socket que o egeon e o curl já usam, com uma conexão persistente para receber eventos. O FFI se reduz a uma função escrita à mão que sobe o core dentro do processo.
Custo dessa escolhaModelos Dart e fromJson à mão; erro de campo só aparece em execução, o que pede testes de contrato com exemplos gravados pelo Rust.
Pacote do emuladorO xterm original (4.0.0) está parado há dois anos. Candidatos levantados: xterm2 (fork mantido, MIT), xterm3 (fork do xterm2, mais recursos, AGPL-3.0-or-later, um autor só) e flterm (motor do Ghostty, MIT, versão 0.0.x, traz biblioteca nativa). Todos têm pouca adoção. Encaminhamento: testar o flterm primeiro; o xterm3 fica como segundo candidato. O teste precisa responder o que a página do pacote não diz: acentos do ABNT2, protocolo Kitty de teclado, leitura do texto da tela por código, como a biblioteca nativa entra no build e a versão mínima do Flutter.
Dúvida técnicaSe o socket unix aguenta o volume dos terminais. É palpite que sim; só um protótipo mede. Se não aguentar, só esse stream vai para FFI cru.

Perguntas abertas

#PerguntaPor que importa
1Qual é o motivo da migração?Se não é para rodar em Linux ou Windows, o driver pode ser só macOS e o trabalho cai. Não há ADR nem motivo registrado.
2A restrição a gerador de código vale também dentro do Dart?Gerência de estado e modelos imutáveis no Flutter costumam puxar gerador (freezed, json_serializable, riverpod_generator).
3Processo único ou core como daemon?Microfone (TCC), identidade por pid e árvore de processos dependem de o app ser o pai do pty. Daemon reabre o ADR-010.
4App novo em paralelo, ou Rust por baixo do app Swift primeiro?Define se existe uma ponte Swift ↔ Rust temporária e por quanto tempo os dois apps convivem.
5Como o core lê a tela do terminal, agora que a grade mora na UI?egeon peek, o marcador de CLI sem gancho e a resolução de links dependem do texto da tela. Com o emulador no Flutter, o core tem de pedir à UI — e sem janela aberta essas três coisas não respondem.
6O que fazer com o nó web sob zoom?WKWebView embutido não acompanha a transformação do canvas.
7Fila de injeção e pedidos de permissão continuam só em memória?Hoje somem no restart.
8Bugs achados no levantamento: corrigir no Swift antes, ou só no porte?Define se o Rust replica o comportamento atual ou já nasce diferente.
9Vidro do macOS 26: aceitar a perda visual?Não há equivalente no Flutter.
